** TODO Better handling of block elements (like `<div>`)                :BUG:
   Will require:
   + Better paragraph tests for various HTML tags.
   + Some kinda decision on how to treat HTML tags.

   Currently, any `<div>` tags used must be placed on a separate lines, like
   this:
   ----------------------------------------
     <div>

     Paragraph 1.

     Paragraph 2.

     </div>
   ----------------------------------------
   If one instead do not separate the `<div>`s and write it like this:
   ----------------------------------------
     <div>
     Paragraph 1.

     Paragraph 2.
     </div>
   ----------------------------------------
   Baremark will naïvely wrap `<p>` tags around the paragraph that contains
   `</div>`, resulting in the following output:
   ----------------------------------------
     <div>
     Paragraph 1.

     <p>Paragraph 2.
     </div></p>
   ----------------------------------------
   Which will in turn will become even more messed up in the browser, because
   the browser (correctly thinking that a `</div>` cannot exist inside a `<p>`
   tag) will break up the `<p>` tag further.
   ----------------------------------------
     <div>
     Paragraph 1.

     <p>Paragraph 2.
     </p></div><p></p>
   ----------------------------------------
   It's not super clear how to actually handle this case. Should `<div>` tags
   be broken up and further parsed? How about other block tags (like
   `<table>`)? What does the CommonMark standard have to say about this?

   Should we append & prepend blank lines to all block tags while processing so
   that these are correctly handled by the paragraph processing?
** TODO Only use `<h1>` once on a page (for page title)
   Hopefully, you’ve come away with these take-homes:

  + Don’t use loads of `<h1>`s. Make `<h1>` the main heading of your page, then
    use `<h2>`, `<h3>`, `<h4>`, etc. in a proper hierarchy without skipping
    levels.
  + `<section>` can be used with aria-label to signal to a screen reader user
    where a particular sub-part of an article begins and ends. Otherwise,
    forget about it, or use another element, such as `<aside aria-label="quick
    summary">` or `<div role="region" aria-label="quick summary">`.
  + `<main>`, `<header>`, `<footer>` and `<nav>` are very useful for screen
    reader users, and entirely transparent to those who don’t use assistive
    technology. So use them.
  + `<article>` isn’t just for blog posts — it’s for any self-contained thing.
    It also helps WatchOS display your content properly.
    (https://www.smashingmagazine.com/2020/01/html5-article-section/#conclusion)

   https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/Heading_Elements#avoid_using_multiple_h1_elements_on_one_page

** TODO Optimize use of preprocessing step
   Currently 'X' is used in regexes to match 'any string that does not contain
   two newlines', this (intentionally) allows for whitespace at the beginning
   and end of the string. This is useful when the string is surrounded by
   markup characters (e.g. inside '[...]' etc.) less so when markup isn't
   surrounding the text (as with paragraphs, atx heading `# ...`), or in a
   [bullet or ordered] list items, where there's no markup character to
   delineate the end).

   Would it be beneficial to be able to use 'Y' in the regexes to indicate a
   string that may not begin or end with a newline, but otherwise match the
   same as 'X'?

** TODO Support reference image inside inline links
   That is, this should work:

       [![alt][imgref]](url)

       [imgref]: imgurl

   Currently, the text is interpreted like this:

       [![alt][imgref]](url)
        ↑↑----alt-----↑↑url↑                       = image found
       [<img src="url" title="" alt="alt][imgref]">
       ↑----------text------------------↑↑imgref↑  = link found
       <a href="imgurl" title=""><img src="url" title="" alt="alt</a>">

   Another, slightly less insane than the current approach would be to escape
   all values outputted into HTML attributes, so that, at least, the above
   weird interpretation doesn't take place? This would cause the image to fail
   in a slightly saner way, at least.
